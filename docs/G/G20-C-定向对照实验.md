## 3. 逐组配对实验详情与因果链核验

### 3.1 实验组 C1：读后生成预算预检失配（`Q01`：`E01, E02, E03`）

- **固定输入**：选中 `Mixtral-of-Experts-2401.04088v1.pdf` v1，问题 `Q01`，`strategy=fts`，`workspace_input_token_limit=32,768`。
- **机制定位**：
  - 在 `app/rag/workspace.py:1153` 中，`read_window` 的预留量被写为 `reserve = 1800 + estimate_input_budget([question, context])`（在 `Q01` 上 `reading_budget = 30,694`，实际装入 15 段共 `30,662` 字节）。
  - 然而在 `app/rag/workspace_generation.py:147-150` 中，`generate_response` 先将 `prompt_data` 序列化为 JSON 字符串放入 `messages[1]["content"]`，再调用 `estimate_input_budget(messages) + 128` 对整个 `messages` 做**第二次 `json.dumps`**。
  - 这导致：① `_INSTRUCTIONS`（1,745 字节）+ `_CHAT_FRAME_RESERVE`（128 字节）+ 每段 `file_name` 与 `reads` 包装开销本身已超过 `1,800` 字节约 433 字节；② 第二次 `json.dumps` 将 15 段 PDF 文本和 JSON 键中的每一个 `"` 与 `\n` 再次转义为 `\"` 和 `\\n`，额外膨胀约 1,044 字节。两者合计使 `generate_response.estimated_input` 达到 `33,939 > 32,768`（超出 1,171 字节）。
- **配对结果**：
  - **Control**：`read_window` 读入 15 段（`ev-1..ev-15`），`generate_response` 报 `budget_exceeded`（`33,939 > 32,768`），0 次 DeepSeek 调用。
  - **Treatment**（仅将 `read_window` 的 `prompt_reserve` 增加 `+1,600` 字节）：`read_window` 读入前 14 段（`page:1..9, 11, 12`，其中 `page:1..3` 即 `E01..E03` 完整保留），`generate_response` 的 `estimated_input` 降至 `32,227 <= 32,768`，1 次 DeepSeek 调用（HTTP 200，耗时 5,552.6 ms）完整答出 `E01`、`E02`、`E03` 全部事实与公式并绑定 `ev-1, ev-2, ev-3`。

### 3.2 实验组 C2：未登记三线表回退父页（`C2a` `Q02`：`E04`）与已登记右子图方位筛选（`C2b` `Q03`：`E05`）

- **C2a（`Q02` 第 8 页 Table 5 三线表）**：
  - **Control**：`object_intent` 识别 `"表格里"` 进入 `_answer_object(kind="table", location=page:8)`。因 LaTeX `booktabs` 三线表无竖线，`_confirmed_pdf_tables` 未登记 `page:8:table:1`，`object_choices` 返回 `[]`（`object_not_found`）。
  - **Treatment**（给定父页 `page:8` 走页级阅读）：`read_window` 读取 `page:8` 原生文本（2,591 字符，`est_in=5,304`），DeepSeek（1 次调用，HTTP 200，2,049.8 ms）从 `page:8` 原生文本中的 Table 5 准确读出 `ArXiv`（`14.0%, 27.9%, 22.7%`）、`DM Mathematics`（`14.1%, 28.4%, 19.7%`）和随机基准 $1/8 = 12.5\%$（First or second choice $1 - \frac{6}{8}\frac{5}{7} \approx 46\%$）。
  - **诊断结论**：按协议，此项**仅计父页级支持（`page:8`）**，精确表对象仍为未登记。但它证明了对于原生文字完整的 PDF 三线表，**答案丢失的直接原因不是缺乏复杂版面/OCR 解析，而是 `_answer_object` 在页面无登记表对象时拒绝回退读取已定位父页的原生文字**。
- **C2b（`Q03` 第 5 页右侧子图 `page:5:image:1`）**：
  - **Control**：`page:5` 登记了两个图像对象：`page:5:image:1`（右图 Perplexity 曲线，`bbox=[0.444992, 0.688088, 0.800889, 0.863947]`，水平中心 `0.623`）和 `page:5:image:2`（左图 Passkey 热力图，`bbox=[0.176471, 0.688093, 0.422344, 0.856755]`，水平中心 `0.299`）。`workspace_objects._on_side(rect, "right")` 硬编码要求 `x0 >= 0.5`，因右图左侧纵轴文字边界在 `0.444992` 而将其筛除，报 `object_not_found`。
  - **Treatment**（允许水平中心 `(x0+x1)/2 >= 0.55` 且 `x0 >= 0.4` 的右图通过 `_on_side("right")`）：`object_choices` 唯一选中 `page:5:image:1`，调用 `qwen3-vl-plus`（HTTP 200，2,878.9 ms，输入裁图 SHA `e96e35c6...`），准确读出横轴 `Context length`、纵轴 `Perplexity`、纵轴刻度 `2.0` 到 `3.8` 及随上下文增加单调下降趋势。同库复跑 `Q10`（`"第 5 页的插图里具体展示了什么结果？"`）仍返回 `object_ambiguous`，无退化。

### 3.3 实验组 C3：长文纯中文双语召回（`C3a` `Q05`：`E07`）与跨文件同池 Jev 排序（`C3b` `Q06`：`E08, E09`）

- **C3a（`Q05` 27 页 DPO 论文第 20 页附录超参）**：
  - **Control (`fts`)**：纯中文问句在英文 PDF 中 `fts_seed_count=0`，回退 `page_browse_fallback` 只取 `page:1..12`，`read_window` 读到 `page:7` 耗尽窗口预算（`page:20` 在 Layer 2 漏召回），随后在 Layer 5 触发 `budget_exceeded`（`33,614 > 32,768`）。
  - **Treatment Arm 1 (`bilingual` only)**：仅启用 `WORKSPACE_RETRIEVAL_STRATEGY=bilingual`。`BilingualRewriter` 生成英文查询 `"In the appendix implementation details of this paper, what are the default optimizer, learning rate, number of linear warmup steps, and batch size respectively?..."`，在 FTS 中将 **`page:20` 召回至第 1 名**（`selected = ['page:20', 'page:23', 'page:7', 'page:3']`），且 `read_window` 已将 `page:20` 完整读入 `ev-7`（**Layer 2、Layer 3、Layer 4 全部救回**）。但因单文件 `read_window` 在读完 4 个优先页后继续从 `page:1` 顺读填满窗口，再次在 Layer 5 触发 `budget_exceeded`（`33,720 > 32,768`）。
  - **Treatment Arm 2 (`bilingual` + `C1` 窗口预留对齐)**：`est_in = 31,881 <= 32,768`，DeepSeek 生成成功，准确答出 `β = 0.1`、`batch size = 64`、`RMSprop`、`1e-6`、`150` 步线性预热及 TL;DR 摘要 `β = 0.5`，引用 `ev-6` (`page:20`)。
- **C3b（`Q06` 跨文件 `Mixtral` 微调方法 `E08` + `DPO` 附录摘要/默认 $\beta$ `E09`）**：
  - **第一重发现（`_fuse` 中的无文字图片占位挤出效应）**：在默认 `bilingual` 与 `jev` 下，`BilingualRewriter` 的英文改写查询已经在 `alternate_pool` 的 **第 6 名** 召回了 `DPO page:20`（`('bb81', 'page:20')`）！然而 `StructureSearcher` 为 `Mixtral page:2` 和 `Mixtral page:6` 附加了无文字的结构邻居图片对象 `page:2:image:1`（`text=""`）与 `page:6:image:1`（`text=""`）。因为这两个无文字图片对象在 `original_pool` 和 `alternate_pool` 中都出现了，`_fuse` 给它们的 RRF 分数（`~0.0284`）高于只出现在 `alternate_pool` 第 6 名的文本页 `DPO page:20`（`1/66 = 0.01515`），导致 `DPO page:20` 被挤到融合池第 13 名（恰好掉出 `pool_cap=12`）！

## 4. 不能排除的竞争解释与边界说明

1. **`C1` / `C3a` 的窗口预留对齐 vs 真实 Token 计数**：
   - `estimate_input_budget` 使用的是 UTF-8 JSON 字节长度近似而非 tokenizer 的真实 BPE token 数。虽然在 `read_window` 增加 `+1,600` 字节预留消除了 `read_window` 与 `generate_response` 之间的二次转义内部不一致（救回 `Q01` 与 `Q05`），但在包含大量换行符或特殊字符的极端文档上，只要 `generate_response` 仍对已序列化的 `messages[1]["content"]` 再做一次 `json.dumps` 计数，转义膨胀率仍可能随换行密度波动。根本修复应让 `read_window` 与 `generate_response` 共用同一个单次序列化计量函数。
2. **`C2a` 父页级支持 vs 精确表格裁图**：
   - 给定或回退到父页 `page:8` 原生文字能救回 LaTeX 三线表的**文字问答与页级引用**，但不能自动产生 `page:8:table:1` 的精确表格框裁图（`rendition_kind="object_crop"`）。若用户要求高亮或单独裁剪无竖线三线表，仍需在解析层补充水平三线表边界检测或布局解析。
3. **`C3b` 中 Jev 的收益前提与延迟代价**：
   - `Zev-1` 在 12 个文本候选中展现了对真正包含超参取值的 `DPO page:20`（`0.812`）与仅含正文泛谈的 `DPO page:9`（`0.043`）的强区分力，但它的前提是 **`DPO page:20` 必须先留在传给 Jev 的 12 候选池内**（若 `_fuse` 让无文字图片邻居把 `DPO page:20` 挤到第 13 名，Jev 也无法无中生有）。同时，单次 Jev 真实调用增加约 `2.2–4.5` 秒外部延迟，不宜对单文件短文或已明确页码的问题无条件开启。
