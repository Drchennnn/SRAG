## 结构增益、漏检与代价

### 可观察增益

预先登记的上下文在 5 组用例增加：真实 Notebook 查询得到一个已保存输出、显式 PPT 页得到表格对象、显式 Cell 得到全部三个输出、登记图注得到父页和无文字图像、满 K 样例得到父页。结构候选都带原因和锚点三元组，没有跨文档、跨课程或跨版本扩展。

结构扩展并不等于语义改善。`FFT` 与否定问句都额外带回相邻 `cell:1`，该 Cell 本身不含 FFT；真实 PPTX 还带回同页标题对象。下游必须根据原因、原文与证据预算判断是否使用，不能把“相邻”改写成“问题已命中”。

### 明确漏检与取舍

- 普通 `NotebookImage` 查询在 `K=4` 时只有一个邻接保留槽，因此三个输出只返回 `output:0`；`output:1`、`output:2` 在轨迹中列为上下文漏检。用户显式指定 Cell 后三项全部按顺序返回。
- `np.linalg.solve` 的完整字面串候选在 `K=3` 中存在并标为 `exact_literal`，但 BM25 顺序位于只含分散词元的 `token_component` 之后；`K=1` 时 exact 候选实际漏检。现有 C01 契约只要求复核并标识，不承诺 exact 优先，因此本项仍通过；若产品要承诺 Top-1 代码定位，应先调整排序并重新审核。
- 满 K 样例为引入父页移除了 `page:3`。这是 C01 规定的保留槽取舍，轨迹同时保留 `structure_added` 与 `structure_removed`，不能只报告增益。

### 工程成本

每个策略、每个用例交替运行 3 次，表中时间为该用例中位数；首轮冷启动和原始样本全部保存在 JSON。该微型探针结果如下。

| 指标 | 纯 FTS | FTS + 结构 |
| --- | ---: | ---: |
| 18 个用例中位数的中位数 | 2.982 ms | 3.058 ms |
| 18 个用例中位数之和 | 54.581 ms | 56.318 ms |
| 实际检查的唯一证据数合计 | 20 | 39 |
| 最终候选数合计 | 18 | 32 |
| 检查的一跳边数合计 | 0 | 45 |

时间只代表本机微型 SQLite 工程探针，不是大型课程性能分布。稳定的成本信号是结构策略检查证据约为本组纯 FTS 的 1.95 倍，并额外检查 45 条边；延迟差在约 3 ms 的噪声范围内，不能据此宣称结构策略更快或更慢。
