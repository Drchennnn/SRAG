# 课程资料 RAG：本地存储 + Qwen API 推理的架构草案

> 状态：设计草案（2026-09-23）。本文件描述方法和验证路径，不代表系统已经实现或达到某个准确率。

## 目标与边界

- 首期以课程 `ipynb` 为主要资料，支持指定课程、文件和章节的可溯源问答；后续增量加入 PDF。
- 支持资料的新版本、发布日期和下架。未到发布日期的资料不进入可查询范围。
- 检索链路的模型推理（embedding、重排，以及未来可能的图像描述）全部调用 Qwen 官方 API（阿里云百炼 / DashScope），不在本地或自建服务器部署模型权重。本地/云端只需要承载文件存储、SQLite、Qdrant 和编排代码。
- 先在本地电脑上完成解析、检索链路搭建和评估；成熟后再评估是否把 Qdrant 和编排服务迁往云端。当前云服务器为 4 核、4 GB 内存、40 GB SSD——这个限制主要针对的是本地部署重型模型（如 [Milvus Standalone 的 8 GB 内存要求](https://milvus.io/docs/prerequisite-docker.md)）的场景；既然模型推理不再本地化，实际瓶颈只剩 Qdrant 的数据量和编排服务本身，是否迁移待本地基线跑通后再评估。
- `/Users/Link/Course` 是候选资料来源，不代表所有文件都应入库。导入采用明确的文件白名单，排除虚拟环境、缓存、训练数据集和无关图片。
- 全部走 API 调用意味着课件内容会发送到阿里云处理；这是已知取舍（个人学习资料），需要妥善保管 API Key（不在客户端或仓库中明文存储），并处理好限流重试与网络异常时的降级策略。

## 数据流

```text
选定资料（ipynb；以后加入 PDF）
  → 文件登记与版本检查
  → 按格式解析为统一的章节 / 内容块 / 资源
  → 父子块与少量图表、代码检索表示
  → 调用 Qwen embedding API（dense + sparse）→ Qdrant 索引
  → 查询范围过滤 → 混合召回 → 调用 Qwen 重排 API → 回取父块和原始资源
  → 基于证据回答并引用文件、页码或 cell
```

原始文件和图片资源保留在文件存储中；SQLite 保存文件清单、版本、父块正文与资源关系；Qdrant 保存用于检索的子块及其向量。父块只存一次，检索命中后通过 `parent_id` 回取。

## 各阶段方法

| 阶段                            | 首期采用的方法                                                                                                                                                                                                                                                                                                                                  | 后续扩展或验证点                                                                                                                                                                                                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 文件登记                     | 只导入选定课程文件；计算内容哈希，记录课程、文件路径、资料类型、版本、发布日期和导入状态。重复内容跳过，变更文件形成新版本。                                                                                                                                                                                                                    | Web 上传、定时扫描和权限管理。发布日期由可信输入提供，不从目录名推断。                                                                                                                                                                                                                                     |
| 2. Notebook 解析                | 用 `nbformat` 按原始 cell 顺序读取 Markdown、代码、文本/HTML 输出、图片和附件；不执行 notebook。由 Markdown 标题建立章节路径，保留代码与其输出的关联。                                                                                                                                                                                          | 处理异常或缺失的 cell ID；长输出、报错堆栈和大数组只保留可检索摘要，完整内容仍可回取。抽查确认部分课程存在中文重写版 notebook（中英夹杂、含 LaTeX 公式与 HTML 样式），双语支持是硬需求，不是可选扩展。                                                                                                     |
| 3. PDF 解析                     | 第二批接入：先提取原生文字与版面，再逐页检查文本质量；扫描页或图片型课件按需 OCR。保留页码、表格结构、公式与图表位置。                                                                                                                                                                                                                          | 以 Docling 为首个解析候选；用代表性 PDF 对照解析质量，必要时增加视觉模型描述图表（可调用 `qwen-vl-ocr`/`qwen3-vl` 系列 API，同样不本地部署）。抽查确认样本 PDF（Keynote/Beamer 导出）均有原生文字层，`pdftotext` 可直接提取、无需 OCR；但文本密度低，图表承载了大部分信息，解析时要重视图注/图像描述环节。 |
| 4. 统一内容结构                 | 两种解析器都产出 `document → section → block → asset`。Notebook block 定位到 cell；PDF block 定位到页码与区域。图片二进制不写入向量 payload。                                                                                                                                                                                                   | PPTX/DOCX 可通过新解析器接入同一结构。                                                                                                                                                                                                                                                                     |
| 5. 父子切块                     | 父块是一个有边界的教学单元（小节、短课件页、相关 Markdown＋代码＋输出）；子块是可独立匹配的定义、解释、代码逻辑或图表说明。首轮试验：子块约 300–600 tokens，父块约 1,000–1,800 tokens。标题、公式、函数和图表说明优先保持完整。                                                                                                                 | 用检索题集调整大小和是否需要重叠；不把整本 PDF 或整个 notebook 当父块。                                                                                                                                                                                                                                    |
| 6. 检索表示                     | 每个正文子块附上简短的课程/文件/章节前缀，生成一份 dense 和一份 sparse 表示。图表、复杂表格可有独立文字说明入口，均指回原始资源和父块。调用 embedding API 时索引侧固定使用 `text_type=document`。                                                                                                                                               | 仅当评估显示收益时，为代码用途或章节摘要增加独立入口；先不使用逐 token 的 ColBERT 多向量。                                                                                                                                                                                                                 |
| 7. 向量化（Qwen API）与本地存储 | 调用 `text-embedding-v4`（Qwen3-Embedding 系列，走 DashScope 原生接口而非 OpenAI 兼容模式，才能拿到 sparse 输出）一次获取 1,024 维 dense 与 sparse 词项权重；单次请求最多 10 条文本、单条最多 8,192 token，按批次调用并做限流重试（参考限流：RPM 1,800、TPM 120 万）。Qdrant 本机 Docker 存储向量及可过滤元数据。记录模型版本、维度和索引版本。 | 用课程题集对比同一 API 内的不同配置：更高维度（1,536/2,048）、开启 `instruct` 提示、有无 sparse 融合。更换维度或配置时新建索引并重算向量；暂不做跨供应商模型对比。                                                                                                                                         |
| 8. 查询与召回                   | 先解析用户明确选择的课程/文件范围和当前可见版本；原问题并行走 dense、sparse，使用 RRF 融合候选，查询侧调用 embedding API 时使用 `text_type=query`。保留课程编号、代码符号、公式和否定词。                                                                                                                                                       | 指代不明时补全问题；中文问英文课件时保留原问并增加英文术语查询。HyDE、step-back 和多查询默认关闭，仅在分类评测有收益时启用。                                                                                                                                                                               |
| 9. 重排与回取                   | 对融合后的有限候选调用 `qwen3-rerank` API（单次最多 500 篇候选、单篇最多 4,000 token、请求总 token 上限 12 万）；按 `parent_id` 去重后回取必要父块、相邻 cell、原图或原表，并限制总上下文长度。记录每条证据的具体来源。                                                                                                                         | 关注 API 调用延迟和网络抖动对交互体验的影响，据实测调整候选数量、超时与重试策略；RRF 融合与语义重排分别评估。`gte-rerank` 将于 2026-05-30 停服，不使用。                                                                                                                                                   |
| 10. 回答                        | 后续问答层优先接 GPT（以账户和服务地区实际可用性为前提）；只依据检索证据回答，给出文件名、页码或 cell 引用。资料不足时说明缺口。                                                                                                                                                                                                                | 课程/考试总结走按文件和章节枚举的覆盖流程，再分节汇总；不依赖一次 top-k 查询。                                                                                                                                                                                                                             |
| 11. 增量更新                    | 新文件生成父块、子块和资源后再切换为可见版本；替换或删除文件时同步清理旧子块、派生说明和失效资源。每次导入记录失败与重试状态。                                                                                                                                                                                                                  | Web 上传与自动导入；检索时同时校验 `document_id`、版本和发布日期，避免旧版或未解封内容泄露。                                                                                                                                                                                                               |
| 12. 评估                        | 人工标注约 60–100 个课程问题及原文件页码/cell，覆盖概念、代码、图表、指定文件、跨章节和无答案题。测 `Recall@k`、`nDCG@k`、引用准确性、回答依据、延迟与资源占用。                                                                                                                                                                                | 固定相同题集及证据预算，对比单层块、父子块、混合检索、多表示与重排；总结另测章节覆盖率，增量导入另测旧版本清理。                                                                                                                                                                                           |

## 关键约束

- **Notebook 是首要数据模型。** 一个代码 cell 的输出可能包含图片、HTML 表格或多种 MIME 表示；不能把整份 notebook 转成纯文本后按固定字符数切割。
- **图表说明是检索线索，不是精确事实来源。** 回答图中数值或曲线关系时回取原图、表格或原始输出核对。
- **父子块与多表示可以组合。** 父子块解决“找到细节后补足上下文”，多表示解决“正文之外怎样找到代码、图和表”；不为每个子块复制同一份标题或章节摘要向量。
- **存储与推理分离。** Qdrant、SQLite、原始文件保存在本地（后续可迁移到云端）；embedding、重排以及未来可能的图像描述均调用 Qwen 官方 API，不在本地或自建服务器部署模型权重，云端小机器因此只需承担存储和编排，不必为模型预留内存。
- **全部依赖外部 API。** 需要处理限流重试（embedding 单次请求上限 10 条文本）、网络异常时的降级或重试、API Key 保密，以及课件内容出境到第三方服务的取舍——当前判断为可接受，但应在实现中显式记录这一决定。
- **先测后调。** 上述 token 范围、候选数量和模型均是初始配置；最终以真实课程问题的效果、延迟和内存证据决定。

## 首个可验收里程碑

选取少量具有 Markdown 说明、代码、图片输出的 notebook，完成导入、父子块检索、按文件过滤及 cell 引用；建立一批人工问题，对比纯 dense、dense+sparse、加重排、加父块回取。该基线稳定后，再接入 PDF 和网页问答。
